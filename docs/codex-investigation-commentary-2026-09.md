## Implementation options

- OPTION 1 - Prompt/descriptions plus buffered selective commentary pass-through.
  - Touch points: replace the current "commentary is silent, act directly" wording in `prompts.py:30`-`prompts.py:37`; add PREAMBLES samples to search, MCP, and `music(action=play)` descriptions above; change `huggingface_realtime.py:3522`-`huggingface_realtime.py:3534` and `huggingface_realtime.py:3850`-`huggingface_realtime.py:3868` to buffer commentary audio/transcripts until `response.function_call_arguments.done` identifies a slow tool at `huggingface_realtime.py:3920`-`huggingface_realtime.py:3959`.
  - Tradeoff: Most faithful to the house rule because the model writes the words and slow/fast policy stays in prompt/tool descriptions. More state: response/item correlation, timeout/fallback, transcript handling, and delayed `start_tool` if preamble must finish before execution.
- OPTION 2 - Tool-name allowlist at the suppression point, only if traces prove early metadata.
  - Touch points: extend the `response.output_item.added` branch at `huggingface_realtime.py:3522`-`huggingface_realtime.py:3534` to detect/commentary-allow responses associated with slow tool names; keep the audio/transcript drop branches mostly as they are.
  - Tradeoff: Smallest code change if the endpoint emits the function-call item/name before commentary audio. Current code and tests do not prove that; the DECISIONS watchpoint explicitly warns that late phase metadata makes the seam too late. It also cannot distinguish `music(action=play)` from `music(action=stop)` unless arguments are available early too.
- OPTION 3 - Deterministic ordering by a separate model-composed preamble turn before slow work.
  - Touch points: in `response.function_call_arguments.done` (`huggingface_realtime.py:3920`-`huggingface_realtime.py:3959`), classify slow tool calls, request a short no-tool preamble response composed by the model, wait for that audio path to drain, then start the slow tool and continue the existing tool-result follow-up path.
  - Tradeoff: Best fit if "speak before starting search/music/MCP" is a hard requirement, and still avoids canned app-side TTS. It is the riskiest protocol change: the original response may still be active, the function-call output contract must not be violated, and it adds at least one extra response cycle.
- ORDERING RISK: Prompted preambles are not a hard speak-then-act guarantee. The research note says tool-call preamble examples are concurrent, not sequential (`docs/research-instructing-realtime-voice-2026-09.md:341`-`docs/research-instructing-realtime-voice-2026-09.md:344`), and the skill says speak-then-act is not promptable (`.claude/skills/reachy-instructing-model/SKILL.md:120`-`.claude/skills/reachy-instructing-model/SKILL.md:128`).
