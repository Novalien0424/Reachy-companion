## 1. Instructing vs hard-coding around the model

- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/prompt-engineering. OpenAI frames prompting as high-level behavioral instruction through roles or the instructions parameter; it also warns that model output is non-deterministic and recommends pinned model snapshots plus eval suites for complex apps. This makes prompts a behavior contract, not a substitute for enforcement.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/function-calling. By default, the model determines when and how many tools to use, but tool_choice can force none, auto, required, a specific function, or an allowed subset. That is the product line: use instructions for flexible judgment, use API controls when the allowed action space is non-negotiable.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/agents/guardrails-approvals. OpenAI says guardrails validate input, output, or tool behavior automatically, and human review pauses sensitive tool calls even when the model decided the action is needed. Sensitive effects must therefore be hard-gated outside the model.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/agents/define-agents. Agent config packages model, instructions, tools, guardrails, handoffs, and structured outputs; separate agents are appropriate when roles, model settings, tool surfaces, or approval policies differ. Do not solve tool-permission boundaries with one giant prompt.
- PRACTITIONER - URL: https://www.anthropic.com/engineering/building-effective-agents. Anthropic separates workflows, where code routes steps on predefined paths, from agents, where the LLM controls process and tool use. The practical guidance is to start with the simplest orchestrated pattern and only give autonomy where it buys capability.
- INFERENCE - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. Put semantic policies in prompt text: when to ask, when to act, what to say before a tool call, when to confirm exact identifiers, and how to recover. Hard-code invariants: auth, access control, write approvals, idempotency, billing, retries, rate limits, session closure timing, and validation of all tool inputs and outputs.


## 2. Tool design: names, schemas, descriptions, returns, errors

- PRACTITIONER - URL: https://www.anthropic.com/engineering/writing-tools-for-agents. Anthropic describes tools as a contract between deterministic systems and nondeterministic agents. Design them for agent perception: clear purpose, few overlaps, natural task subdivisions, and enough domain context in descriptions for a new teammate to use correctly.
- PRACTITIONER - URL: https://www.anthropic.com/engineering/writing-tools-for-agents. Namespacing matters when many tools or MCP servers coexist. Service/resource prefixes such as asana_projects_search reduce boundary confusion; evaluate prefix versus suffix schemes because effects vary by model.
- PRACTITIONER - URL: https://www.anthropic.com/engineering/writing-tools-for-agents. Prefer agent-sized tools over raw endpoint wrappers. A single get_customer_context tool can be better than list_customers plus list_transactions plus list_notes because it offloads search and compaction from the model and returns high-signal context.
- OFFICIAL - URL: https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use. Anthropic strict tool use constrains sampling to schema-valid tool inputs and prevents type/required-field breakage. Schema conformance is necessary but not sufficient for correct tool choice or business-policy compliance.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. OpenAI Realtime guidance says tool behavior depends on both prompt and tool spec design. It recommends explicit read/write rules, exact-identifier confirmation rules, failure recovery rules, and instructions to use only actually provided tools.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. For write tools and external effects, prompt the assistant to summarize the intended action, mention the consequence, ask for confirmation, and only state completion after successful tool return. This is still backed by app-side approval for real risk.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. For exact identifiers, collect one value at a time, normalize only clear digits or spelled characters, preserve spoken separators, read numeric IDs back digit by digit, and never call lookup or write tools with guessed, partial, ambiguous, or unconfirmed values.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. Tool output design matters: raw strings that must be repeated verbatim are error-prone. Wrap long or authoritative tool output in a small JSON envelope such as response_text plus require_repeat_verbatim or content_type, and document how the assistant should render it.
- INFERENCE - URL: https://www.anthropic.com/engineering/writing-tools-for-agents and https://developers.openai.com/api/docs/guides/realtime-models-prompting. Return values should be short, typed, and decision-ready: status, user-facing message, machine action flags, retryability, canonical IDs, confidence, next allowed actions, and concise evidence. Avoid dumping full API payloads into the model context.
- INFERENCE - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. Error returns should be model-readable but not raw stack traces: code, category, retryable boolean, user_safe_summary, exact field needing correction, and next_step. Prompt the model not to repeat identical failed calls and to escalate after repeated failures.


## 3. Realtime speech-to-speech: gpt-realtime-2.1 and gpt-realtime-2.1-mini

- OFFICIAL - URL: https://developers.openai.com/api/docs/models/gpt-realtime-2.1. gpt-realtime-2.1 is a Realtime reasoning model with tool use. The model page says it improves alphanumeric recognition, silence and noise handling, and interruption behavior; supports speech-to-speech interactions, configurable reasoning effort, instruction following, and tool use; has 128k context and 32k max output tokens; supports function calling; and does not support structured outputs.
- OFFICIAL - URL: https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini. gpt-realtime-2.1-mini is a distilled reasoning model for faster, lower-cost realtime voice interactions over WebRTC, WebSocket, or SIP. It supports audio/text input, audio/text output, function calling, and reasoning tokens, but the model page also marks structured outputs as unsupported.
- OFFICIAL - URL: https://developers.openai.com/api/reference/realtime. Realtime session/call configuration exposes prompt, tool_choice, tools, parallel_tool_calls for reasoning Realtime models, and a reasoning parameter. This means you can combine natural-language instructions with hard API constraints on the tool surface and reasoning setting.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. Prompt structure should be explicit and sectioned: role/personality, task context, conversation flow, rules, exact-entity handling, tools, tool-failure behavior, and safety/escalation. The Tools section should say when and when not to call each function, what arguments to collect, what to say while running, and how to handle partial or failed results.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. To get speech before or around tool calls, instruct the model at the global or per-tool level. OpenAI examples include saying a short line while calling a tool, per-tool labels such as PROACTIVE, CONFIRMATION FIRST, and PREAMBLES, and sample preamble phrases in tool descriptions.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. If instructed to be proactive and skip confirmation, a realtime model may directly call the tool with no response audio. If that is bad UX, soften the tool-use rule and add an explicit preamble rule for slow, visible, or high-latency tools.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. Use a no-op wait_for_user tool for silence, background noise, hold music, TV audio, side conversations, or speech not addressed to the assistant. This gives the model a valid non-speaking action rather than forcing filler speech.
- OFFICIAL - URL: https://developers.openai.com/api/reference/realtime-server-events/conversation/item/input_audio_transcription/completed. Realtime APIs expose function-call argument completion events such as response.function_call_arguments.done with call_id, item_id, name, and JSON arguments. Treat tool events as machine-facing state and spoken message output as user-facing audio; do not parse speech as the tool contract.
- INFERENCE - URL: https://model-spec.openai.com/ and https://developers.openai.com/api/docs/guides/prompt-engineering. The public docs distinguish higher-authority instructions from user input, while Realtime exposes separate message/tool events. If an implementation exposes message versus commentary channels, put user-audible speech in message/final output and tool calls or tool preambles in the tool/commentary path; never rely on hidden spoken text to execute side effects.
- OFFICIAL - URL: https://docs.livekit.io/agents/prebuilt/tools/end-call-tool/. LiveKit EndCallTool is the cleanest documented session-ending pattern: when end_call is called, the agent generates a final response from end_instructions, the session shuts down after the response completes, and the room can be deleted to disconnect participants.
- OFFICIAL - URL: https://docs.vapi.ai/tools/default-tools. Vapi exposes endCall as a default assistant tool when included in the assistant tools array, so hang-up is modeled as an explicit callable capability rather than an unstructured prompt wish.
- INFERENCE - URL: https://docs.livekit.io/agents/prebuilt/tools/end-call-tool/ and https://developers.openai.com/api/docs/guides/realtime-models-prompting. For raw OpenAI Realtime, implement end_session_after_goodbye as a tool or app-side state transition that returns a final response_text, wait for response.done or audio completion, then close WebRTC/WebSocket/SIP. For sleep mode, use a non-speaking wait/sleep tool and wake-word or user-speech logic instead of having the model keep saying it is waiting.


## 4. Small distilled model limits and mitigations

- OFFICIAL - URL: https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini. The mini model is explicitly distilled for faster, lower-cost realtime voice interactions. Distillation and lower cost are product advantages, but use narrower prompts and tool surfaces because smaller models usually have less spare capacity for long instruction stacks.
- RESEARCH - URL: https://huggingface.co/papers/2509.18420. IFEval-FC reports that existing function-calling benchmarks often miss format-instruction adherence inside JSON schema descriptions. Its 750-case benchmark found even advanced proprietary models can fail basic formatting rules, so description-following cannot be assumed.
- RESEARCH - URL: https://www.llmreference.com/benchmark/ifeval. General IFEval leaderboards show large gaps between frontier and smaller models on checkable instruction following. This is directional, not a deployment proof, but it supports testing distilled models against the exact constraints you need.
- OFFICIAL - URL: https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use. Grammar/schema-constrained tool input is a strong mitigation where available. It guarantees schema shape and type conformance, though it does not prove that the selected tool or semantic value is correct.
- PRACTITIONER - URL: https://www.anthropic.com/engineering/writing-tools-for-agents. Anthropic recommends evaluation loops that collect accuracy, runtime, number of tool calls, token use, and tool errors. That is especially important for mini models because failures often show up as wrong tool choice, redundant calls, or mishandled tool responses.
- INFERENCE - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting and https://huggingface.co/papers/2509.18420. Mitigate distilled-model brittleness by reducing tool count, using unambiguous names and parameter names, adding use/avoid examples per tool, using exact-identifier workflows, validating all arguments externally, retrying with correction prompts, escalating to a larger model or human for high-risk writes, and returning compact JSON tool outputs instead of prose blobs.
- INFERENCE - URL: https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini. For gpt-realtime-2.1-mini, good fit areas are greeting, triage, FAQ, simple read-only lookups, wake/silence handling, and low-risk slot filling. Use gpt-realtime-2.1 or a non-realtime larger model for long multi-step planning, ambiguous recovery, policy-heavy flows, and expensive irreversible actions.


## 5. Reasoning effort on realtime models: latency versus tool reliability

- OFFICIAL - URL: https://developers.openai.com/api/docs/models/gpt-realtime-2.1. OpenAI states that gpt-realtime-2.1 supports configurable reasoning effort and that higher effort can increase latency and output token usage. Reasoning effort is therefore a runtime quality/latency knob, not a free reliability upgrade.
- OFFICIAL - URL: https://developers.openai.com/api/reference/realtime. Realtime session and call configuration include a reasoning parameter for reasoning-capable realtime models such as gpt-realtime-2. Use it deliberately per agent, session, or task segment.
- OFFICIAL - URL: https://developers.openai.com/api/docs/guides/latency-optimization. Latency is a first-class production concern for realtime and streaming applications. Tool preambles and lower-latency settings can improve perceived responsiveness, while excessive reasoning can make a voice agent feel stalled.
- PRACTITIONER - URL: https://www.anthropic.com/engineering/writing-tools-for-agents. Anthropic recommends measuring total runtime, tool-call count, token consumption, and tool errors in evals. This is the right way to decide whether raising reasoning effort beats better tool specs or orchestration.
- INFERENCE - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. Tool reliability usually improves first from clearer tool names, narrower tool sets, use/avoid rules, exact-identifier workflows, and structured tool returns. Increase reasoning effort only for turns where the model must reconcile ambiguous state, choose among multiple tools, or plan a multi-step path.
- INFERENCE - URL: https://developers.openai.com/api/docs/models/gpt-realtime-2.1. Suggested realtime policy: low or default effort for small talk, silence/no-op, FAQ, and simple read-only lookup; medium effort for slot collection plus one tool; high effort only for multi-tool diagnosis, conflicting user state, repeated failures, or escalation summaries. Pair high effort with brief spoken preambles so the user hears progress before the longer think/tool path finishes.

- RESEARCH - URL: https://mathllm.github.io/VoiceAssistantEval/. VoiceAssistant-Eval benchmarks AI assistants across listening, speaking, and viewing; its 2025 leaderboard includes GPT-4o-Audio, Step-Audio, Qwen2.5-Omni, Kimi-Audio, GLM-4-Voice, and bilingual LLaMA-Omni variants across 13 tasks.
- RESEARCH - URL: https://arxiv.org/abs/2503.20215. Qwen2.5-Omni is a 2025 omni-modal technical report for models that can process text, images, audio, and video and generate text and speech. Chinese voice agents should benchmark these native audio models where latency, speech naturalness, and Mandarin robustness matter.
- RESEARCH - URL: https://arxiv.org/abs/2504.18425. Kimi-Audio is a 2025 open-source audio foundation model report covering audio understanding, generation, and conversation. Public eval summaries show strong Mandarin ASR results on AISHELL and WenetSpeech, relevant to Chinese-first voice capture.
- OFFICIAL - URL: https://developers.openai.com/api/docs/models/gpt-realtime-2.1. OpenAI gpt-realtime-2.1 improves alphanumeric recognition, silence/noise handling, and interruption behavior, but the model page does not provide Chinese-specific benchmark claims. Validate Mandarin, Traditional Chinese, code-switching, and local acoustic conditions yourself.
- INFERENCE - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting and https://github.com/Tencent/VCB-Bench. Chinese-primary prompts should be authored primarily in the target spoken variety, not translated from English after the fact. For Taiwan-facing agents, prefer Traditional Chinese output, Taiwan terminology, local phone/address formats, and explicit rules for Mandarin-English code-switching, Latin letters, product IDs, and email spelling.
- INFERENCE - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. Exact-identifier handling is even more important in Chinese voice flows because users may mix Mandarin numerals, English letters, aliases, and punctuation names. Capture raw transcript plus normalized value, confirm numeric IDs digit by digit, and confirm email or Latin identifiers character by character before tool calls.
- INFERENCE - URL: https://github.com/Tencent/VCB-Bench. Build a Chinese voice regression set with accents, fast/quiet speech, background TV or chat, code-switching, casual corrections, and multi-turn topic shifts. Use human review for low-frequency failure modes because automatic WER alone misses whether the assistant chose the right tool and spoke naturally.


## 7. Operational pattern to use in production

- INFERENCE - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting. Use a short, sectioned realtime prompt: identity and language, scope, conversation flow, speech style, exact-entity workflow, tool policy, per-tool use/avoid rules, failure recovery, silence/no-op behavior, and escalation/end-session behavior.
- INFERENCE - URL: https://developers.openai.com/api/docs/guides/function-calling. Use tool_choice and dynamic tool lists as control-plane mechanisms. For example, expose only read tools before authentication, add write tools only after confirmation state is reached, and force none during a final goodbye if the app must prevent late tool calls.
- INFERENCE - URL: https://docs.livekit.io/agents/logic/agents-handoffs/. Use separate agents or handoffs when the permission boundary changes: anonymous triage, authenticated account support, payments, human transfer, and post-call summarization should not all share one prompt and one tool list.
- INFERENCE - URL: https://www.anthropic.com/engineering/writing-tools-for-agents. Tool descriptions are prompts. Review and test them like prompts, including negative examples, failure cases, and held-out evals. Watch transcripts, not only aggregate scores, because model explanations often omit the real confusion source.
- RESEARCH - URL: https://gorilla.cs.berkeley.edu/leaderboard.html. BFCL V4 tracks tool-use accuracy, agentic behavior, multi-turn interaction, hallucination measurement, format sensitivity, and latency. Use BFCL-like categories when building local evals for tool choice and argument correctness.
- RESEARCH - URL: https://huggingface.co/papers/2509.18420. Add IFEval-FC-style checks for formatting requirements embedded in schema descriptions. A model can pass JSON schema but still violate ISO dates, punctuation bans, quoting rules, casing, or local phone/email conventions unless tested.
- INFERENCE - URL: https://developers.openai.com/api/docs/guides/realtime-models-prompting and https://docs.livekit.io/agents/prebuilt/tools/end-call-tool/. Session-ending rule: model decides conversational readiness, but app/framework owns finalization. The reliable sequence is detect goodbye or call end tool, generate final audible response, wait for completion, then sleep or hang up. Do not close transport before final audio completes.
- INFERENCE - URL: https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini and https://github.com/Tencent/VCB-Bench. For Chinese-primary mini-model deployments, keep the prompt thinner than the full model prompt, localize all examples, expose fewer tools, and run a Chinese speech eval set before increasing autonomy.
